# Frontend Payment Receipt Relay Architecture (Issue #20)

## Executive Summary
This document outlines the architectural standard for migrating payment receipt (UPI screenshot) uploads from direct Cloudflare R2 uploads to a robust, high-concurrency server-side disk storage pipeline managed by our dedicated backend (`snist-website-bn` / `c3_backend`).

By offloading file handling and storage to our server, we eliminate Cloudflare storage costs while ensuring high concurrency resilience, zero memory bloating on serverless frontend functions, and seamless environment portability between local development and baremetal production infrastructure.

---

## 1. High-Level Architecture & Request Flow

Instead of the Next.js serverless functions connecting to AWS S3 / Cloudflare R2 SDKs, the frontend acts as a stateless, highly performant validation and relay tier.

```
┌──────────────┐         FormData          ┌─────────────────────────┐
│ User Browser ├──────────────────────────►│ Next.js Frontend (c3)   │
└──────────────┘                           │ /api/digital-india/sub  │
                                           └────────────┬────────────┘
                                                        │
                                          Server-to-Server Relay
                                           (Streamed HTTP POST)
                                                        │
                                                        ▼
                                           ┌─────────────────────────┐
                                           │ Express Backend (BN)    │
                                           │ /api/digital-india/sub  │
                                           └────────────┬────────────┘
                                                        │
                                        Atomic Pipeline & Compression
                                                        │
                                                        ▼
                                           ┌─────────────────────────┐
                                           │ Mounted Disk Volume     │
                                           │ uploads/receipts/YYYY/MM│
                                           └─────────────────────────┘
```

## 2. Frontend Responsibilities & Concurrency Protection

### A. Stateless Streaming Relay
When a user submits the registration form (`POST /api/digital-india/submit`):
1. **Lightweight Validation:** The Next.js API route validates basic field requirements, phone/email regex, and checks in-memory rate limits (`src/lib/rate-limit.ts`) to prevent abuse before processing large payloads.
2. **Payload Forwarding:** The raw `FormData` (including the multipart file stream) is forwarded directly to the backend service via `fetch(`${process.env.NEXT_PUBLIC_API_URL}/api/digital-india/submit`, { method: 'POST', body: formData })`.
3. **No RAM Buffering:** By forwarding the `FormData` directly, the serverless frontend avoids buffering multi-megabyte images in runtime memory, preventing cold-start memory spikes and Vercel execution timeouts under high user concurrency.

### B. Admin Verification Proxy (`GET /api/admin/digital-india/screenshot`)
When administrators review payment receipts on the dashboard:
1. The dashboard requests `/api/admin/digital-india/screenshot?id=<submission_id>`.
2. The frontend proxies the request to the backend with the administrative `x-api-key` header.
3. The backend streams the image bytes directly back to the admin interface.
4. **Backward Compatibility:** If the returned or stored record references an old `https://pub-*.r2.dev/...` URL, the relay transparently resolves and serves the image without breaking legacy dashboard entries.

## 3. Deterministic & Human-Readable Receipt Naming Standard

To ensure payment screenshots can be verified rapidly by administrators—even during manual terminal audits or bulk CSV/ZIP exports—receipt filenames generated by the backend MUST incorporate essential identification fields from the submitted form:

### Standard Naming Format
```text
utr_<sanitized_utrId>___phone_<sanitized_phone>___<sanitized_team_or_name>___<short_hash>.<ext>
```
*Example:* `utr_418293847561___phone_9876543210___team_cyber_warriors___a8f9b.webp`

### Verification Benefits
- **Instant UTR Reconciliation:** Prefixing filenames with `utr_<utrId>` allows administrators to find any screenshot instantly using terminal wildcard searches (`ls *418293847561*`) without needing to query MongoDB first.
- **Cross-Checking Submitter Identity:** Including sanitized phone numbers and team names enables manual human audits directly from file manager interfaces during high-stress registration verification windows.

## 4. Environment Configuration

To configure the frontend relay target, maintain the following variables in `.env`:

```env
# URL of the Express backend repository (snist-website-bn)
NEXT_PUBLIC_API_URL=http://localhost:8000

# Administrative API key required for secured screenshot viewing relays
API_KEY=your_secure_shared_api_key
```

When deploying to production, `NEXT_PUBLIC_API_URL` should point to the baremetal or containerized backend domain (e.g., `https://api.cloudcommunityclub.com`).

---

## 5. Operational Best Practices for Contributors

1. **Do NOT re-add Direct Cloudflare R2 / AWS SDK Dependencies:** Keep the frontend codebase lightweight. All file transformations, disk writes, and database transactions are owned exclusively by the backend service.
2. **Handle Relay Timeouts Gracefully:** Ensure client-side forms display clear loading states (`Loader2` spinner) and error toasts if the backend relay experiences temporary network latency under heavy surge traffic.
3. **Preserve Rate Limits:** Maintain strict IP-based sliding window rate limits on all form submission endpoints to protect downstream disk storage from denial-of-service (DoS) upload floods.
